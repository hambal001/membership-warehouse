# Membership Data Warehouse

A small data warehouse for a gym/membership business, built with **Python, SQL and SQLite**:
raw CSV files go in, a **star schema** and **analytics marts** come out, and automated
**data-quality checks** fail the run if anything is wrong.

The data is **synthetic** (generated by `warehouse/generate.py`, no real people). It is
deliberately messy, with duplicate rows, negative amounts, invalid dates and orphan references,
so the cleaning and quality logic has real problems to catch. The business model follows the
membership, payment and check-in systems I built for a gym in Google Sheets.

## Architecture

```
raw CSVs  ->  staging (clean + quarantine)  ->  star schema  ->  marts (views)  ->  report
members       stg_* tables                      dim_date          mart_monthly_revenue
plans         rejected_rows (with reasons)      dim_plan          mart_member_activity (churn flag)
payments                                        dim_member        mart_cohort_retention
checkins                                        fact_payment      mart_peak_hours
                                                fact_checkin
                                  data-quality checks run after every load
```

| Layer | What it does |
|-------|--------------|
| `stage.py` | Reads CSVs, fixes types, removes duplicates, and **quarantines** bad rows in `rejected_rows` with a reason (invalid date, unknown member, duplicate id, ...) instead of silently dropping them |
| `sql/01_schema.sql` | Star schema with primary keys, foreign keys, unique business keys and indexes |
| `sql/02_load.sql` | Idempotent loads: dimension **upserts** (`ON CONFLICT DO UPDATE`) and fact inserts that skip existing business keys, so re-runs are safe and new rows load incrementally. The date dimension is generated in SQL with a recursive CTE |
| `sql/03_marts.sql` | Business views: monthly revenue, member activity with a churn-risk flag, cohort retention, peak hours |
| `checks.py` | 8 checks (referential integrity, positive amounts, staged-vs-loaded reconciliation, ...). Any violation raises an error and the run is logged as `failed` |

## Run it

```bash
pip install -r requirements.txt
python -m pytest -q                 # 10 tests
python -m warehouse.run --generate  # generate data, build the warehouse, run checks
python -m warehouse.report          # print headline numbers from the marts
```

Open `warehouse.db` in any SQLite viewer (for example DB Browser for SQLite) and query the marts:

```sql
SELECT * FROM mart_member_activity WHERE at_risk = 1 ORDER BY days_since_last_visit DESC;
```

## Example output (synthetic data, 300 members)

- 1,607 payments and 17,178 check-ins loaded; 36 bad rows quarantined, with a reason for each
- 115 active members, 25 flagged at risk (active, no visit for 21+ days)
- Monthly revenue and cohort retention tables for the last 18 months

These numbers come from random synthetic data, so they describe the pipeline, not a real business.

## Tests

- Cleaning: each kind of bad row is rejected with the right reason
- Idempotency: running twice gives identical row counts
- Incremental load: appending a new payment adds exactly one row
- Dimension update: a changed member status is overwritten, not duplicated
- Marts: revenue, churn flag and cohort retention are checked against hand-calculated values
- Quality checks: deliberately corrupting the warehouse makes the checks fail
- Generator: same seed gives byte-identical files; full run on messy generated data passes

## Design notes and limits

- **SCD type 1**: dimensions overwrite old values, so history of a member's plan changes is not kept. A next step would be type 2 (valid_from / valid_to).
- **SQLite-specific SQL**: the marts use `strftime` and `julianday`. Moving to PostgreSQL would mean swapping these for `date_trunc` and date arithmetic.
- **Batch, not streaming**: each run re-reads the raw files; the idempotent loads make that cheap and safe.

## Ideas to extend it

- Move to PostgreSQL and model the marts with dbt
- Orchestrate with Airflow or Prefect
- Add a Power BI or Streamlit dashboard on the marts
- Add SCD type 2 for member plan history
